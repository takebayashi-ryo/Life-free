# リリース手順

変更を本番に届けるまでの決まった流れ。**順番を飛ばさないこと。**

## 1. 現在地を確認

```bash
git status --short
git log --oneline -1
```

未コミットの変更が何なのか、自分が把握しているものか確認する。
身に覚えのない変更があれば、進める前にユーザーに確認する。

## 2. 検証（両方必須）

```bash
npm run typecheck
npm run build
```

⚠️ **`build` だけでは型エラーを検出できない。** Vite は内部で esbuild を使っており、
型注釈を剥がすだけで型検査をしない。`typecheck` を省略しないこと。

どちらかが失敗したら、そこで止めて直す。失敗したままコミットしない。

## 3. コミット

日本語で、**何をしたかではなく、なぜしたか**を書く。

```
<一行の要約>

<背景: どんな問題があったか>

<変更の内容>
```

良い例:

```
起動時に総資産が初期値で一瞬表示される問題を修正

ロード中(isLoadingRecords=true)は config.initialCash の値が
totalAssetsとして表示されていた。ロード中は'¥—'プレースホルダーを
表示し、誤表示を防ぐ。
```

- モデル名・ツール名をコミットメッセージに入れない
- 「〜を追加」だけで終わらせない。理由を書く

## 4. push

```bash
git push origin main
```

大きな変更（新機能・データモデル変更）の場合は、先に `claude/<機能名>` ブランチで
プレビューを確認してから main に squash merge する。

```bash
git merge --squash origin/claude/<機能名>
```

## 5. CI の結果を確認（省略しない）

push しただけで終わらせない。**必ず結果を見る。**

`mcp__github__actions_list` で `method: "list_workflow_runs"`, `resource_id: "ci.yml"` を指定。
結果が大きすぎる場合はファイルに保存されるので、python で `head_sha` / `status` / `conclusion` を抜く。

CI は約20秒で終わる。queued のうちは少し待ってから再確認する。

失敗していたら、その場で直してもう一度回す。赤いまま放置しない。

## 6. CLAUDE.md を更新

新機能・新タブ・データモデルの変更をしたときは必ず。

- 「現在の状態」に反映
- 未マージのブランチがあれば記載、無くなったら消す
- 設計判断の理由を残す（次のセッションが同じ検討を繰り返さないため）
- localStorage キーやテーブルを追加したら一覧に足す

置換で更新するときは、**置換が成立したか必ず検証する**。
文字列が一致せず無言で失敗することがある。

```python
assert old in s, "対象が見つからない"
```

## 7. ユーザーに報告

- CI の結果（緑か赤か）
- 何が変わったか
- **触って確認してほしい箇所**を具体的に
- 意図的にやらなかったこと、残った課題があれば正直に

反映には Vercel のデプロイで2〜3分かかることを添える。
スマホで見るときは一度リロードが必要。
